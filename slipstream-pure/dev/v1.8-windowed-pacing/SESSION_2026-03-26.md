# Сессия 2026-03-26: v1.8 Windowed Pacing

## Цель
Объединить sliding window (v1.6) + pacing (v1.7) для увеличения скорости через pipelining.
Каждый poll должен получать РАЗНЫЙ batch из серверного окна.

## Архитектура v1.8

### Сервер: DownstreamWindow + rotation
- `DownstreamWindow`: sliding window из 4 batch'ей (WINDOW_SIZE=4)
- Каждый batch помечен 4-байтным `batch_id` prefix (BE u32)
- `send_cursor`: round-robin ротация — каждый poll возвращает следующий batch
- ACK от клиента: удаляются batch'и с `id <= client_ack`, окно дозаполняется
- На Connect: окно полностью сбрасывается

### Клиент: BatchTracker + pipelined pump
- `BatchTracker` (BTreeSet) вместо hash-based dedup
- Contiguous ACK: наивысший batch_id без пропусков ниже
- Connection-level retry: до 5 попыток (из v1.6)
- Buffered initial data (TLS ClientHello) для retry

### Эволюция pump'а в этой сессии

#### Итерация 1: send_parallel_good(3) + rotation
- Отправляет 1 запрос через 3 resolver'а, возвращает ПЕРВЫЙ ответ
- Сервер ротирует → 3 разных batch'а → клиент видит только 1
- Результат: **2/5 HTTPS, ~2 KB/s**
- Проблема: 2 из 3 ответов теряются, пропущенные batch'и → ACK не продвигается

#### Итерация 2: + 10ms pacing после получения данных
- В итерации 1 цикл не спал после получения данных (каждый ответ был новый)
- Добавлен sleep(10ms) после успешного получения
- Результат: **3/5 HTTPS, ~2 KB/s**
- Чуть лучше reliability, скорость та же

#### Итерация 3: 3 отдельных poll'а (разные seq), await all
- Каждый poll — уникальный seq, идёт через свой good path
- Все 3 ответа обрабатываются (не только первый)
- Результат: **3/5 HTTPS, ~2 KB/s** (50KB download), ~6.8 KB/s (5KB download)
- **Pipelining подтверждён** — batch'и приходят не по порядку, BatchTracker собирает:
  ```
  pump: recv batch=3 ack_now=0 pending=[3]
  pump: recv batch=2 ack_now=0 pending=[2, 3]
  pump: recv batch=4 ack_now=0 pending=[2, 3, 4]
  pump: recv batch=1 ack_now=4 pending=[]
  pump: recv batch=8 ack_now=4 pending=[8]
  pump: recv batch=5 ack_now=5 pending=[8]
  pump: recv batch=7 ack_now=5 pending=[7, 8]
  pump: recv batch=6 ack_now=8 pending=[]
  pump: recv batch=9 ack_now=9 pending=[]
  pump: recv batch=11 ack_now=9 pending=[11]
  pump: recv batch=10 ack_now=11 pending=[]
  ```
- 11 batch'ей за ~0.8с, zero gaps after reorder

#### Итерация 4: Continuous spawner (MAX_INFLIGHT=3)
- Непрерывный поток poll'ов через channel
- Spawner создаёт новый poll каждые 10ms
- Receiver обрабатывает ответы по мере прихода
- Результат: **1/5 HTTPS, 21 B/s** — СЛОМАНО
- Проблема: флуд resolver'ов, ~100 RPS

#### Итерация 5: Continuous spawner + 40ms pacing
- Spawner увеличен до 40ms между poll'ами (вместо 10ms)
- Результат: **1/5 HTTPS, 0 B/s** — СЛОМАНО
- Проблема: 40ms между ОДИНОЧНЫМИ poll'ами слишком медленно, первый poll таймаутит пока третий отправляется

#### Итерация 5b: Burst mode (3 poll'а пачкой) + 15/25ms pacing
- Возврат к подходу iter3 (3 poll'а пачкой, await all)
- Pacing: 15ms после данных, 25ms на пустом ответе
- ~3 poll / 65-75ms ≈ 40-45 RPS
- Результат: **5/5 HTTPS (100%), 1.8 KB/s** (50KB download)
- **Лучшая HTTPS reliability за всю историю проекта** (не считая v1.0-EARLY с 0 скоростью)

### Ключевые находки (single-resolver)
1. **Пайплайнинг идеально работает** — 0 дубликатов, 0 пропусков, ACK бежит
2. **Bottleneck был sleep** — 15ms pacing замедлял в 4 раза. Без sleep: RTT сам пейсит.
3. **MAX_RAW=1000 + no sleep = 19 KB/s** — рекорд проекта
4. **WINDOW=8 хуже чем 4** — больше разброс batch_id → pending растёт → ACK блокируется
5. **Channel spawner не работает** — async poll'ы с устаревшим ACK → дубли → ACK не продвигается

## Оптимальная конфигурация

**Подробное исследование:** `RESEARCH_v1.8.md`

Параметр | Значение | Почему
---|---|---
PIPELINE_WIDTH | 3 | = WINDOW_SIZE-1, 4-й batch = retransmit буфер
WINDOW_SIZE | 4 | Больше → разброс batch_id → ACK блокируется
timeout | 500ms | 200ms обрезает медленные но валидные ответы
sleep | 0 | RTT (~50ms) сам пейсит, sleep замедляет в 4 раза
MAX_RAW | 1000 | Работает через Google EDNS0, запас для адаптивного

## Ключевые находки

### 1. Pipelining работает (iter3)
Серверная rotation отдаёт разные batch'и разным poll'ам.
BatchTracker корректно собирает out-of-order batch'и.
11 batch'ей за 0.8с = пропускная способность ×3 от v1.7.

### 2. send_parallel_good несовместим с rotation
`send_parallel_good(3)` отправляет 1 запрос → 3 resolver'а → возвращает 1 ответ.
С rotation сервер отдаёт 3 разных batch'а, но клиент видит только 1.
Пропущенные batch'и блокируют ACK → ретрансмиты → медленно.

### 3. Отдельные poll'ы (iter3) — правильный подход
3 poll'а с уникальными seq, каждый через свой resolver.
Все 3 ответа обрабатываются → 3 batch'а за один RTT.
Но await-all добавляет latency (ждём самый медленный).

### 4. Continuous spawner (iter4) — слишком агрессивен
100 poll/s → resolver rate-limiting → полный провал.
Нужен контроль RPS, не превышать ~30-50 req/s.
