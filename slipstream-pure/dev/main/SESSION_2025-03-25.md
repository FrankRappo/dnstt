# Сессия 2025-03-25: Connection-level retry + Sliding Window

## Что было сделано

### 1. Connection-level retry (клиент)
- Буферизация initial data (TLS ClientHello) перед split TCP stream
- Retry loop: до 5 попыток, каждая — новый stream_id → Connect → отправка ClientHello → poll → ожидание downstream
- При timeout — tear down, retry с новым stream
- Upstream seq начинается после initial_data chunks

### 2. Sliding window downstream (сервер)
- Заменён stop-and-wait на sliding window (WINDOW_SIZE=4)
- Сервер заполняет окно до 4 batch'ей вперёд, не дожидаясь ACK
- При ACK — удаляются подтверждённые batch'и, окно дозаполняется
- Каждый batch маркирован 4-байтным batch_id prefix

### 3. BatchTracker (клиент)
- Заменён hash-based dedup на batch_id tracking
- BTreeSet для отслеживания полученных batch'ей
- Contiguous ACK: ack = макс непрерывно полученный batch_id
- Новая функция dispatch_downstream_with_batch вместо dispatch_downstream_inline

### 4. DsHashRing (клиент, промежуточный шаг)
- Заменял single-hash dedup, сейчас заменён на BatchTracker
- Можно удалить если остался в коде

### 5. Batch ID prefix strip (клиент)
- dispatch_downstream_raw (вызывается из send_packet) теперь отрезает 4-байтный prefix
- Без этого HTTP ломался (данные парсились как мусор)

## Что работает

### Sliding window — ПОДТВЕРЖДЕНО
```
pump: recv batch=1 ack_now=1 pending=[]
pump: recv batch=2 ack_now=2 pending=[]
...
pump: recv batch=13 ack_now=13 pending=[]
```
13 batch'ей за 0.8 секунды, zero gaps, contiguous ACK 1→13.
Раньше (stop-and-wait): 7 batch'ей × ~300ms = 2+ секунды, с потерями.

### Диагностика серверная — ПОДТВЕРЖДЕНА
Логи показывают полный flow:
```
ds: ack=0 win_before=[] after_ack=0 queue=5 new=[1,2,3,4] returning=Some((1, 504))
ds: ack=1 win_before=[1,2,3,4] after_ack=3 queue=2 new=[5,6] returning=Some((2, 504))
```

## Что НЕ работает

### HTTPS success rate: ~20-40% (baseline без наших изменений тоже ~30%)
Оригинальный бинарник v1.5 + оригинальный сервер: 3/10 HTTPS.
Наш код с sliding window: 2-4/10 HTTPS.

### Причины (диагностировано):
1. **DNS delivery ~60-70% per-attempt** — и upstream и downstream
2. **Два failure mode:**
   - Initial downstream не приходит (40%) — Connect/ClientHello не доходят до сервера
   - Downstream пришёл, upstream TLS Finished не доходит (20%) — соединение зависает
3. **Это НЕ баг кода** — оригинальный бинарник показывает тот же результат

### Найденные и исправленные баги:
1. **ACK exact-match deadlock** (сервер) — `client_ack == batch_id` вместо range-based. Клиент ACK=10, сервер batch_id=11 → вечный цикл
2. **Hash dedup ложные ACK** (клиент) — single hash сравнение позволяло поздним ответам от медленных resolver'ов инкрементировать ACK
3. **dispatch_downstream_raw без strip** (клиент) — batch_id prefix передавался в TunnelPacket::decode_all как мусор → HTTP ломался
4. **Window не заполнялся** (сервер) — первая версия возвращала первый batch сразу, не заполняя окно

## Нерешённые вопросы

### Почему DNS delivery ~60-70%?
Не диагностировано. Возможные причины:
- Resolver rate-limiting (слишком много запросов к одному authoritative)
- Часть good paths реально мёртвые
- Время суток / нагрузка на resolver'ы
- conntrack на VPS (упоминалось в ROADMAP)

### Нужна диагностика:
- Per-resolver loss rate (какие resolver'ы работают, какие нет)
- Round-trip time per resolver
- Проверить conntrack на сервере (nf_conntrack_max, udp_timeout)

## Не откатываем?
Sliding window — **оставляем**. Он работает и объективно лучше stop-and-wait:
- Downstream delivery за 0.8с вместо 2+с
- Нет ACK deadlock
- Batch tracking вместо хрупкого hash dedup

Проблема не в протоколе — протокол работает. Проблема в DNS transport layer.
