# План дальнейшей работы — Slipstream Pure

## Ключевая находка сессии 25-26 марта

**Причина падения HTTPS reliability с 100% (v1.0) до 40% (v1.5):**
Resolver rate-limiting.

v1.0 отправлял ~5-10 DNS запросов/сек (1 sequential poll) → resolver'ы не лимитят → 100% HTTPS.
v1.5 отправлял ~30+ DNS запросов/сек (10 parallel polls) → resolver'ы дропают → 40% HTTPS.

**Доказательство:** v1.7 с 3 parallel polls (вместо 10) → 80% HTTPS + 8 KB/s.
Уменьшение агрессивности polling напрямую повышает reliability.

## Текущий лучший результат

**v1.7-PACING: 80% HTTPS, 8 KB/s**

Основа: v1.5-STABLE с изменённым pump:
- `send_parallel_good` 10 → 3
- sleep при пустом ответе 5ms → 15ms
- sleep при ошибке 20ms → 30ms

## Теоретический предел одного потока

`batch_size / RTT = 500 байт / 50мс = 10 KB/s`

v1.7 даёт 8 KB/s — близко к пределу.

## Как разогнать скорость

### Вариант 1: Sliding window + pacing (приоритет)
Совместить v1.6 (sliding window) с v1.7 (pacing).
- Сервер шлёт 4 batch'а вперёд (не ждёт ACK каждого)
- Клиент poll'ит через 3 parallel (не 15)
- Каждый poll получает СЛЕДУЮЩИЙ batch, не тот же самый
- Теория: ×4 скорость = 32 KB/s
- **Риск:** sliding window + batch_id prefix добавляет сложность.
  Надо аккуратно совместить с pacing.

### Вариант 2: Увеличить batch_size через EDNS0
Сейчас MAX_RAW=500 (ограничение DNS UDP 512 байт).
EDNS0 позволяет до 4096 байт. Если отправлять 2000 байт за batch:
- Меньше round-trip'ов
- Скорость: 2000 / 50мс = 40 KB/s
- **Риск:** не все resolver'ы поддерживают большие ответы.
  Нужно фильтровать: использовать большие batch'и только через EDNS0-совместимые resolver'ы.
  Документация отмечает: "DNS-ответы > 512 байт — резолверы дропают/обрезают"

### Вариант 3: Больше resolver'ов (v2.5 из ROADMAP)
Сейчас 18 resolver'ов. С 50-100 resolver'ами:
- По 1 запросу каждому → 0 rate-limiting
- 50 запросов/сек без потерь
- Скорость: 50 × 500 = 25 KB/s
- **Зависимость:** DNS-сканер (v2.5 из ROADMAP)

### Вариант 4: N sub-streams (v2.0 из ROADMAP)
N независимых ACK-потоков через разные resolver'ы.
- Каждый поток 8 KB/s через свои 3 resolver'а
- 5 потоков × 8 KB/s = 40 KB/s
- 10 потоков × 8 KB/s = 80 KB/s
- **Самый масштабируемый подход**

### Вариант 5: Pipelining
Клиент шлёт несколько poll'ов с разными seq одновременно.
Сервер отвечает на каждый разным batch'ем (вместо одного pending).
По сути sliding window но на уровне poll'ов, не batch'ей.

## Рекомендуемый порядок

1. ~~Sliding window + pacing~~ — **СДЕЛАНО (v1.8-iter9b, 19 KB/s на 1 Google)**
2. **Адаптивный batch size** — сначала отработать на одном resolver'е, потом масштабировать.
   **Этап A (один resolver):**
   - Discovery probe: клиент шлёт тестовые запросы разного размера → определяет max response size
   - Клиент в poll payload передаёт `max_bytes` → сервер подстраивает batch size
   - Протестировать реальные лимиты Google (1000? 1400? 2000?)
   - Ожидание: +10-20% скорости (21→25 KB/s)
   **Этап B (multi-resolver):**
   - Каждый resolver получает свой max_bytes при discovery
   - Сервер адаптирует batch size per-poll (не per-session)
   - Мелкие resolver'ы (512B) работают рядом с крупными (1400B)
   - Без этого нельзя масштабировать — одни обрежут, другие недогрузятся
3. **Multi-resolver тест** — подключить 5-10 resolver'ов с текущей конфигурацией.
   Проверить линейность масштабирования (19 KB/s × N).
4. **DNS-сканер** — найти 200+ рабочих resolver'ов. При 19 KB/s на resolver → 200 × 19 = 3.8 MB/s
5. **N sub-streams** — параллельные потоки через разные resolver'ы
